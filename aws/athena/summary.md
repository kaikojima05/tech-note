## Athena について

S3 に保存されたファイルを SQL で検索・出力できる AWS のサービス
<br />Athena 本体はクエリエンジンのため、データを保持していないことが特徴
<br />また、Lambda と同じくサーバーレスのため、実行時にしか起動しないことも特徴である
<br />起動時間 ≠ 料金ではなく、スキャン量 = 料金になっている（大量にスキャンすればその分起動時間も伸びるため、起動時間 = 料金の認識でもそこまで違うものでもないが...）

## 実態

**Trino** という OSS の SQL クエリエンジンをマネージドサービスにしたものが **Athena** になる
この **Trino** は、複数のデータソース（MySQL, PostgreSQL, S3, CSV）に対して、内部でコネクタを介すことによって、横断的にアクセスすることができる
また、一つのマシンではなく複数ワーカー（マシン）で分散して処理を実行することができるため、大規模データの取り扱いに長けている

## メリット

- DB エンジンではない為、どんな形式のファイルを読むかで検索コストが大きく変わる
  - 例えば Parquet 形式でファイルを配置することによって、パフォーマンスが改善する
- 従量課金制のため、実行しない場面では料金がかからないことや、クエリやファイル形式を改善することでコストを抑えることが可能

## デメリット

- 従量課金制のため、クエリ実行時に取得範囲を絞らないことによって、不必要に大量のデータを読み込んでしまうことによるコストが肥大化する可能性がある
- ローカルでの検証が難しい場面がある
  - ローカルでも Athena を使用できれば無視できる問題なのだが、`ローカルではDBを立てて本番では Athena を使用する` ような方法だと、同じメソッドを使用しても Athena だけ違う値を返す場合がある
  - ローカルに Trino を立てる、という手法もあるが、JVM 上で動作するソフトウェアなので、セットアップのコストが開発のコストに見合わないケースが往々にしてある（ありそう）
